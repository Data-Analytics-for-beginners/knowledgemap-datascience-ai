# analysis/

NLP-аналіз тем на основі зібраних статей.

## Призначення

Виявити приховані теми та зв'язки між ними на основі заголовків, тегів та описів статей.

## Структура

| Файл | Статус | Призначення |
| --- | --- | --- |
| `clean_data.py` | ✅ готово | Очищення `data/raw/articles_raw.csv` → `data/processed/articles_clean.csv` |
| `data_stats.py` | ✅ готово | Precheck-звіт по очищеному датасету перед тематичним моделюванням |
| `text_preprocessing.py` | ✅ готово | Токенізація, стоп-слова, лематизація (без зовнішніх моделей) |
| `topic_modeling.py` | ✅ готово | TF-IDF + LDA (scikit-learn) для виявлення тем |
| `tag_network.py` | 🔜 план | Матриця спільної появи тегів (co-occurrence) для графа |

## Очищення даних (`clean_data.py`)

```bash
python analysis/clean_data.py           # data/raw/articles_raw.csv → data/processed/
python analysis/clean_data.py -v        # + детальні логи
```

### Що робить скрипт

CSV читається через `pandas.read_csv` — повноцінний RFC 4180 парсер. Наївний
`line.split(",")` тут ламається: заголовки на кшталт
`"Gemini 3.7 Flash: Features, Benchmarks, and Pricing"` містять коми всередині лапок.

Фільтри застосовуються послідовно, кожен зі своєю причиною видалення:

1. **`missing url`** — рядок без URL (страховка).
2. **`missing published_date (certification page)`** — сторінки сертифікацій
   (`sql-certification`, `power-bi-certification`, `GitHub-certifications`).
   Вони живуть під `/blog/` і тому проходять URL-фільтр скрапера, але не мають
   ані `datePublished`, ані автора, ані тегів — саме порожня дата надійно
   відрізняє їх від статей.
3. **`unparsable published_date`** — дата не парситься як `%Y-%m-%d`. Парсинг
   навмисно строгий: `fetch_articles.py` вже нормалізує дати, тож інший формат
   означає, що скрапер змінився, і це має бути помітно, а не «тихо виправлено».
4. **`empty title`** / **`empty excerpt`** — базова валідація текстових полів,
   з яких далі будується корпус для TF-IDF/LDA.
5. **`duplicate url`** — дедуплікація за `url` (лишається перший рядок). Це
   другий рубіж захисту: `fetch_articles.merge_rows` вже дедуплікує при зборі.

### Результати

| Файл | Вміст |
| --- | --- |
| `data/processed/articles_clean.csv` | Очищені статті + похідні колонки |
| `data/processed/articles_dropped.csv` | Видалені рядки з колонкою `drop_reason` |
| `data/processed/cleaning_report.json` | Лічильники: скільки рядків видалено і чому |

Схема `articles_clean.csv` — це вихідні колонки
(`title, url, published_date, author, tags, excerpt, scraped_at`) плюс похідні:

- `published_year` — рік публікації (`int`)
- `published_month` — місяць у форматі `YYYY-MM`
- `tag_count` — кількість тегів у рядку

Скрипт **ідемпотентний**: повторний запуск читає той самий `raw/` і дає
байт-у-байт ідентичний результат. Сирі дані ніколи не змінюються.

### Робота з тегами

У CSV колонка `tags` лишається у вигляді рядка з роздільником `|`. Це свідоме
рішення: записаний у комірку `"['a', 'b']"` довелося б розбирати через
`ast.literal_eval` — крихко й із втратами. Для аналізу є окремі функції:

```python
from analysis.clean_data import load_clean, split_tags, tag_frequencies

df = load_clean()                 # + tags_list (list[str]), published_at (datetime)
df["tags_list"].head()            # [['Deep Learning', 'Large Language Models'], ...]

split_tags(df["tags"])            # те саме для довільного DataFrame
tag_frequencies(df).head(20)      # топ-20 тегів за кількістю статей
```

`split_tags` повертає `[]` для статті без тегів (а не `[""]`), тож `.explode()`
і `len()` працюють коректно.

## Статистика після очищення (`data_stats.py`)

```bash
python analysis/data_stats.py
python analysis/data_stats.py --top 30 --output data/processed/data_stats.txt
```

Друкує текстовий precheck-звіт із чотирьох блоків:

1. **Cleaning summary** — скільки рядків видалено і з якої причини (читає
   `cleaning_report.json`), із прикладами URL.
2. **Corpus overview** — розмір корпусу, діапазон дат, довжина `title`/`excerpt`
   у словах (чи вистачить тексту для LDA).
3. **Publication dates** — розподіл публікацій за роками з ASCII-гістограмою та
   часткою статей за останні 12 місяців.
4. **Tags** — топ-20 тегів, покриття тегами, скільки тегів зустрічається лише в
   одній статті (довжина «хвоста» таксономії).

Запускати перед тематичним моделюванням: перекошений за періодом корпус або
надто довгий хвіст тегів змінюють інтерпретацію тем.

## Попередня обробка тексту (`text_preprocessing.py`)

Модуль без зовнішніх залежностей: токенізатор, список англійських стоп-слів і
лематизатор написані на стандартній бібліотеці. Три рішення, які варто знати:

**Жодних завантажень моделей.** І `nltk`, і `spaCy` при першому використанні
тягнуть корпус/модель із мережі. Мережевий виклик усередині кроку аналізу
робить пайплайн невідтворюваним у чистому checkout і в CI, тому все зроблено
локально.

**Доменні терміни — не шум.** `SQL`, `AI`, `R`, `BI`, `C++` зникли б від
наївного фільтра «викидати токени коротші за 3 символи» або від стемера. Вони
захищені множиною `DOMAIN_TERMS`, а варіанти написання зводяться до однієї
форми через `CANONICAL_TERMS` (`LLMs` → `llm`, `sklearn` → `scikit-learn`).
Токенізатор навмисно зберігає `c++`, `a/b`, `gpt-4`, `scikit-learn` цілими.

**Лематизація зважає на корпус.** Сліпе відрізання суфіксів робить із `coding`
→ `cod`, а з `writing` → `writ`, і тоді назви тем стають нечитабельними.
Тому: правила множини застосовуються завжди (вони безпечні — `queries` →
`query`, `models` → `model`), а суфікси `-ing`/`-ed` відрізаються **лише якщо
отримана основа реально трапляється в корпусі** (`coding` → `code`, бо `code`
у корпусі є; `writing` лишається як є). Суфікс `-er` не чіпаємо взагалі —
інакше `engineer` став би `engine`, а `career` → `care`.

## Тематичне моделювання (`topic_modeling.py`)

```bash
python analysis/topic_modeling.py             # повний цикл із підбором k
python analysis/topic_modeling.py --topics 12 # фіксована кількість тем
python analysis/topic_modeling.py --topic-range 6 24 2 -v
python analysis/topic_modeling.py --vectorizer count   # LDA на «сирих» частотах
```

### Пайплайн

```
title + excerpt → препроцесинг → TF-IDF → LDA для кількох k
                → вибір k за coherence → назви тем → звірка з тегами → артефакти
```

### Чому scikit-learn, а не gensim

`gensim` — класична реалізація LDA і дає `CoherenceModel` «з коробки», але
версія 4.3 досі імпортує `scipy.linalg.triu`, який прибрали в scipy 1.13
(тобто на стеку Python 3.12 / numpy 2 вона просто не імпортується).
`scikit-learn` і так потрібен для TF-IDF, тож `LatentDirichletAllocation`
залишає одну залежність замість двох. Єдине, що втрачаємо — coherence — тут
реалізовано вручну як `umass_coherence` (потрібні лише лічильники спільної
появи слів у документах).

### Чому TF-IDF на вході LDA

Формально LDA — генеративна модель над **частотами**, і подача TF-IDF є
задокументованим наближенням, а не канонічним використанням. На коротких
текстах воно працює добре: саме IDF не дає словам `data` й `learn`
домінувати в кожній темі. Прапорець `--vectorizer count` вмикає підручниковий
варіант — решта пайплайну ідентична.

### Підбір кількості тем

Перебираються k = 8, 10, …, 22 (`--topic-range`). Для кожного k рахується:

- **UMass coherence** — чи справді ключові слова теми трапляються в одних
  статтях (чим ближче до 0, тим краще); за нею й обирається k;
- **perplexity** — довідково.

### Звірка з таксономією тегів

Колонка `tags` (73 унікальні теги) — це людська таксономія DataCamp, тобто
приблизна «земля правди». Для кожного тега всередині теми рахується **lift** —
у скільки разів тег частіший у темі, ніж у корпусі загалом. `lift ≈ 1` означає
наскрізний тег, який нічого не підтверджує; `lift > 2` — тема справді
відповідає окремій частині таксономії. Це якісна перевірка, а не метрика
якості моделі.

### Артефакти

| Файл | Вміст |
| --- | --- |
| `data/processed/topics.json` | Теми: `topic_id`, назва, топ-10 слів із вагами, теги з lift, приклади статей, матриця подібності та готовий список ребер |
| `data/processed/articles_with_topics.csv` | Усі колонки `articles_clean.csv` + `topic_id`, `topic_prob`, `topic_second_id`, `topic_second_prob`, `topic_label`, `topic_keywords` |
| `analysis/topic_modeling_report.md` | Звіт українською: параметри, таблиця підбору k, опис кожної теми, звірка з тегами |

Формат навмисно розрахований на наступний етап (`viz/`):
`topics[].topic_id` — вузли графа, `edges` (`{source, target, weight}` за
косинусною подібністю розподілів слів) — готові зважені ребра. Альтернативний
спосіб побудувати ребра — пари `topic_id` / `topic_second_id` у CSV: скільки
статей поєднують дві теми.

Скрипт **детермінований**: `random_state=42` і `learning_method="batch"`, тож
повторний запуск на тому самому вході дає ті самі теми.

## Методологія

1. Очищення даних (`clean_data.py`) + precheck (`data_stats.py`)
2. Попередня обробка тексту (`text_preprocessing.py`)
3. Векторизація TF-IDF + тематичне моделювання LDA (`topic_modeling.py`)
4. Побудова графа тем і візуалізація (`viz/`, наступний етап)

## Результат

- `../data/processed/articles_clean.csv` — очищений датасет для NLP
- `../data/processed/topics.json` — виявлені теми з ключовими словами та ребрами
- `../data/processed/articles_with_topics.csv` — статті з домінантною темою

## Тести

```bash
python tests/test_clean_data.py
python tests/test_topic_modeling.py
```

Офлайн-перевірки `clean_data.py` на власних CSV-фікстурах: коми в лапках,
порожні поля як `""` (а не `NaN`), кожен фільтр, розбиття тегів, ідемпотентність.

`test_topic_modeling.py` працює на невеликому синтетичному корпусі (18 статей,
три теми) — реальний датасет і мережа не потрібні: токенізація доменних
термінів, стоп-слова, лематизація, векторизація, кількість тем на виході LDA,
присвоєння домінантної теми, назви тем, lift тегів, детермінованість і повний
цикл CLI із записом усіх трьох артефактів.
